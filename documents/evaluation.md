
# 評価

## No code

- メリットは抽象化されている部分。

- 構造上、パフォーマンスに問題が出る場合もある。

- 非エンジニアが、社内で使うちょっとしたツールを、ぱぱっと作るのはいいかも。

- このてのツールのよくあるパターンだけど、コードより難しい可能性はある。

- 潰しがきかない。

- UIがカオス。（製作者以外は誰もわからない）

- 潰しがきかないとか、コードのほうが好きなどの理由により、No codeはエンジニアがやりたがらないため、エンジニアの確保が難しい。

## ビジュアルスクリプティング

- bubbleで使うビジュアルスクリプティングは、コードを書かないでいい仕組みではなくて、コードをGUIで表現した仕組み。

- ビジュアルスクリプティングは難しいので、これが身につく時点で、コードはもっと簡単に身につくと思う。

- ビジュアルスクリプティングは、アセンブラ並みかそれ以上に、カオスになりやすい。（実装した人以外は誰もわからない）

- ビジュアルスクリプティングは、構造上、合理的な実装が難しくなりやすい。

- ビジュアルスクリプティングは、No codeという名前の、2次元のコード。

## No codeの問題点

簡単なようで難しい。

## No codeの可能性

ガチで、非エンジニア向けに仕上げれば、可能性はあるかもしれない。

具体的には、こんな感じ。

### 機能

- DBスキーマを含んだ、認証、EC、CMS、ツイートのブロックを用意する。
- ユーザーは、組み立てるだけで、コードは書かない。
- シンプルで迷わないけど、できることに限界がある構造。

### デザイン

- 汎用的なデザインをいくつか用意する。
- ユーザーは、微調整だけできるようにして、しなくても、それなりに見えるように、普遍的なデザインを網羅する。
- 世の中に本当に必要とされているデザインなんて、５パターンもないと思う。

### UI

- nocodeと言いながら、作った人以外は誰も把握ができないような、何が何だかわからないUIの場合もあるので、引き算が必要。
- ブロックを追加すると、ブロックの管理画面へのリンクが表示されるだけとかにする。
- 誰でも、一目でわかるインターフェース。


今は、どっちつかずなので、結果的に、簡単なようで難しい。

自称No codeであるビジュアルスクリプティングを採用した時点で、コードのほうが都合がいいことが多くなる。

つまり、本当に都合がいいNo codeにしたいなら、ビジュアルスクリプティングがなくても成立するようにしないといけないと思う。
