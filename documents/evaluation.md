
# 評価

## No code

- メリットは抽象化されている部分。

- 構造上、パフォーマンスに問題が出る場合もある。

- 非エンジニアが、社内で使うちょっとしたツールを、ぱぱっと作るのはいいかも。

- このてのツールのよくあるパターンだけど、コードより難しい可能性はある。

- 潰しがきかない。

- UIがカオス。（製作者以外は誰もわからない）

- 潰しがきかないとか、コードのほうが好きなどの理由により、No codeはエンジニアがやりたがらないため、エンジニアの確保が難しい。

- かといって、非エンジニアが何とかなる範囲は、限られている。

- gitで管理ができない。

## ビジュアルスクリプティング

- No codeで使うビジュアルスクリプティングは、コードを書かないでいい仕組みではなくて、コードをGUIで表現した仕組み。

- ビジュアルスクリプティングは難しいので、これが身につく時点で、コードはもっと簡単に身につくと思う。

- ビジュアルスクリプティングは、アセンブラ並みかそれ以上に、カオスになりやすい。（実装した人以外は誰もわからない）

- ビジュアルスクリプティングは、構造上、合理的な実装が難しくなりやすい。

- ビジュアルスクリプティングは、No codeという名前の、2次元のコード。

- gitで管理ができない。（中には、gitに保存だけはできるビジュアルスクリプティングもあるけど、当然ながら、変更差分は、摩訶不思議になる。）

- No codeといいながら、ビジュアルスクリプティングは、エンジニアじゃないと手に負えなくなる。

- 上記の通り、構造化が難しいため、複雑になると、エンジニアでも手に負えなくなる。

## No codeの問題点

簡単なようで難しい。

## No codeの可能性

ガチで、非エンジニア向けに仕上げれば、可能性はあるかもしれない。

その際に、構造やUIのバランスは、ユーザーが何をすればいいかわかりやすく工夫されているゲームの仕組みが参考になると思う。

具体的には、こんな感じ。

### 機能

- DBスキーマを含んだ、認証、EC、CMS、ツイートのブロックを用意する。
- ユーザーは、組み立てるだけで、コードは書かない。
- シンプルで迷わないけど、できることに限界がある構造。

### デザイン

- 汎用的なデザインをいくつか用意する。
- ユーザーは、微調整だけできるようにして、しなくても、それなりに見えるように、普遍的なデザインを網羅する。
- 世の中のいいデザインの最大公約数を求めていくと、５パターンくらいになると思うので、それを一通り用意する。

### UI

- No codeと言いながら、作った人以外は誰も把握ができないような、何が何だかわからないUIの場合もあるので、引き算が必要。（ミニマリスト的な発想）
- ブロックを追加すると、ブロックの管理画面へのリンクが表示されるだけとかにする。
- 誰でも、一目でわかるインターフェース。

### システム管理

- 内部的に、gitなどで管理して、安定したロールバックなどを可能にする。変更差分はAIで文章化しておく。（コードがなく、組み合わせと微調整のデータしかないなら可能になるかも）

今は、どっちつかずなので、結果的に、簡単なようで難しい。

自称No codeであるビジュアルスクリプティングを採用した時点で、コードのほうが都合がいいことが多くなる。

つまり、本当に都合がいいNo codeにしたいなら、ビジュアルスクリプティングがなくても成立するようにしないといけないと思う。

ただし、こうすると、どうしても必要なニーズがあっても実装できない場合がでてくる。

そのため、かなり限定的な利用方法になると思う。

あくまで、可能性であり、これが事業になるかは不明。

多くの事業者は、おそらくは、これでは事業にならないと判断したため、ビジュアルスクリプティングを追加しているのだと思う。

つまり、No codeを丁度いい形で成立すること自体が不可能な可能性もある。

## No codeのバランス

シンプルにすると、本来の役割になるけど、できることが限定的になり実務では難しい。

逆に、できることを増やすと、本来の役割を果たせなくなり、最終的には、シンプルにみえる複雑な開発環境が出来上がる。

## 別のNo codeの可能性

かなり限定的な用途に限った関数的な機能だけ提供する。

この場合は、上記のNo codeのバランスの悪影響が少なくなるかも。

## gitが使えない問題点

システムは厳密さが必要だけど、gitが使えないと、この厳密さの維持が困難になりやすい。

厳密さが不要な、実証実験程度であれば、問題ない場合もあると思う。

## エンジニア視点

上記の通り、No codeは潰しがきかない上に、実証実験程度でのみ使うのが無難な仕組み。

その割には、覚えることが多い。

つまり、No code専門というニッチなエンジニアという方向性になると思う。

さらに、日本の現場は保守的なことが多いためNo codeなどは採用されにくいため、海外との取引を基準に考えたほうがいいので、英語が話せる人のほうがいいと思う。

ただし、No codeは、ベンダー依存のため、突然、案件がなくなる可能性はあるので、その点は注意が必要だと思う。

livewireも潰しがきかないけど、それとは比べ物にならないくらい潰しがきかない技術なので、選択する場合は、状況が変わったら職種を変えるなどの、ある程度の覚悟は必要だと思う。
